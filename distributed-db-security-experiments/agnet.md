# Codex 实验执行任务书：分布式数据库攻击与防御补充实验

## 背景与目标

当前论文第2章系统讨论了分布式数据库系统中的新型攻击，包括单分片泛洪、共识层 Leader DoS、跨分片事务抢跑等；但第4章实证评估主要覆盖 SQL 注入、密码攻击和数据级加密开销。请补充一组可复现的分布式架构攻击与防御实验，用于回应审稿意见中“理论分类与实证评估覆盖度不匹配”的问题。

核心目标不是证明某个真实产品存在漏洞，而是在可控环境中量化三类分布式架构风险及对应防御机制的效果：

1. 数据分发机制风险：单分片泛洪攻击与限流/负载均衡防御。
2. 共识与副本调度风险：TiDB Leader 压力攻击/网络扰动下的可用性与恢复能力。
3. 跨分片事务顺序风险：异步窗口下的抢占式提交模拟评估。

## 总体要求

- 所有实验必须在内网、容器或受控测试环境中运行，不得攻击任何公网服务。
- 输出必须可复现，包括脚本、配置、运行命令、原始结果、汇总表格和论文可直接使用的文字分析。
- 不要声称“TiDB 存在跨分片抢跑漏洞”或“复现了真实共识漏洞”。TiDB 用作真实分布式数据库对照与恢复能力评估对象。
- PostgreSQL 3 分片环境用于机制模拟，TiDB 用于真实分布式数据库对照。
- 指标体系尽量与论文第4章已有实验保持一致：成功率/检测率、延迟、P95/P99、CPU、失败率、恢复时间、性能开销。

## 实验一：单分片泛洪攻击与限流/负载均衡防御评估

### 实验对象

构建两类环境：

- PostgreSQL 3 分片：3 个 PostgreSQL 容器分别作为 shard-0、shard-1、shard-2，前置一个简单路由层，按 `user_id` 或 `item_id` 哈希/取模路由。
- TiDB：部署最小可运行 TiDB 集群，建议包含 1 个 TiDB Server、3 个 TiKV、3 个 PD。若服务器资源不足，可先降低规模，但要在报告里说明。

### 攻击场景

设置三组流量：

- 均匀流量：请求均匀分布到 3 个分片。
- 中度热点：70% 请求集中到单一分片或同一 key 范围。
- 高度热点：90% 请求集中到单一分片或同一 key 范围。

请求类型建议使用读写混合负载，例如：

- 70% `SELECT`
- 20% `UPDATE`
- 10% `INSERT`

### 防御组

至少实现四组对照：

- Baseline：无防御。
- 分片级限流：对单一分片的最大并发或 QPS 设限。
- 热点 key 限流：对同一 `item_id`、`account_id` 或 key range 设限。
- 请求队列隔离/负载均衡：热点请求进入独立队列，非热点请求不被拖垮；读请求可做副本或缓存式分流模拟。

### 指标

记录以下数据：

- 总 QPS/TPS。
- 平均延迟、P95、P99 延迟。
- 请求失败率、超时率。
- 每个分片的 CPU、内存、连接数或活跃事务数。
- 热点分片与非热点分片负载差异。
- 防御开销：正常均匀流量下启用限流/队列后带来的吞吐下降或延迟增加。

### 预期论文结论

该实验应支撑如下结论：

> 单分片泛洪攻击的请求可以表现为合法数据库访问，因此传统基于 SQL 语法特征的 WAF/IDS 难以直接识别。分片级限流、热点 key 隔离和队列化机制能够显著降低热点分片对全局吞吐和尾延迟的影响，但会引入一定的调度开销和正常流量下的延迟损失。

## 实验二：TiDB 共识 Leader 压力攻击/网络扰动下的可用性与恢复评估

### 实验对象

使用 TiDB 集群：

- 1 个或 2 个 TiDB Server。
- 3 个 TiKV 节点。
- 3 个 PD 节点。

建议使用 TiUP 或 Docker Compose 部署。若使用 TiUP，需在 README 中写清版本、拓扑和启动命令。

### 攻击/扰动场景

本实验不要写成“复现共识漏洞”，而应写成：

> 共识 Leader 节点压力攻击与网络扰动下的可用性评估。

至少设计三组：

- 正常基线：无扰动，运行标准读写负载。
- Leader 压力：定位热点 Region Leader 所在 TiKV，对该节点施加 CPU 压力、I/O 压力或请求压力。
- 网络扰动：对 Leader 所在 TiKV 注入延迟、抖动或短时丢包，可使用 `tc/netem` 或容器网络限制。

如能实现，加入恢复组：

- 解除压力后观察恢复时间。
- 触发或等待 Leader 转移，观察业务恢复情况。

### 指标

记录以下数据：

- 正常期、攻击/扰动期、恢复期的 QPS/TPS。
- 平均延迟、P95、P99 延迟。
- 请求失败率、超时率。
- Leader 转移是否发生。
- Leader 转移耗时。
- 恢复时间，即指标恢复到基线 90% 或 95% 所需时间。
- TiKV 节点 CPU、内存、磁盘 I/O。

### 防御/缓解分析

重点观察：

- TiDB/PD 调度是否能迁移热点或 Leader。
- 限流是否能降低尾延迟。
- 热点调度与 Leader 转移对可用性的恢复效果。

### 预期论文结论

该实验应支撑如下结论：

> 基于 Leader 的共识和副本调度机制在正常情况下能够提高一致性与系统效率，但当 Leader 所在节点遭受资源压力或网络扰动时，系统可用性会出现明显退化。调度、Leader 转移和限流机制能够缓解故障影响，但恢复过程存在非零时间窗口，说明分布式数据库防御不能只依赖应用层或外围规则，还需要关注共识层和调度层的韧性。

## 实验三：跨分片事务异步窗口下的抢占式提交模拟评估

### 定位

本实验使用 PostgreSQL 3 分片构建可控模拟环境，用于抽象刻画跨分片事务在处理阶段与提交阶段之间存在异步窗口时可能产生的顺序操控风险。

不要写成：

> 复现 TiDB 跨分片抢跑漏洞。

应写成：

> 跨分片事务异步窗口下的抢占式提交模拟。

TiDB 可作为成熟分布式事务机制的对照环境，用来说明全局时间戳、事务冲突检测和提交顺序约束对该类风险的缓解效果。

### 业务场景

建议使用“库存抢购”或“账户转账”场景。优先推荐库存抢购，容易解释：

- shard-0：用户请求或用户账户。
- shard-1：商品库存。
- shard-2：订单确认。

一次跨分片事务流程：

1. 在 shard-0 校验用户资格。
2. 在 shard-1 扣减库存。
3. 在 shard-2 写入订单确认。

### 攻击模拟

构造两个事务：

- `T_victim`：正常用户事务，先到达系统。
- `T_attacker`：攻击者事务，后到达入口，但利用阶段间延迟，在目标分片上先完成库存扣减或订单确认。

模拟方式：

- 在 `T_victim` 完成 shard-0 校验后，人为加入网络/处理延迟。
- `T_attacker` 在延迟窗口内发起冲突请求。
- 如果 `T_attacker` 先在 shard-1 完成库存扣减，则记为一次抢占式提交成功。

### 防御组

至少实现以下对照：

- 无防御：各分片按本地到达顺序处理。
- 全局序列号：入口路由层为事务分配全局递增序号，目标分片按序提交。
- 版本检查/OCC：提交前检查库存版本号或账户版本号，冲突则回滚后到事务。
- 冲突 key 队列化：同一商品、账户或资产 key 的跨分片事务串行执行。
- 两阶段提交模拟：prepare 阶段锁定目标资源，commit 阶段统一确认。

### 指标

记录以下数据：

- 抢占式提交成功率：后到事务先提交的比例。
- 一致性违规率：库存超卖、余额异常、订单顺序反转等。
- 事务回滚率。
- 平均延迟、P95、P99 延迟。
- TPS/QPS。
- 防御开销：全局排序、冲突队列、OCC 或两阶段提交引入的吞吐下降与延迟增加。

### 预期论文结论

该实验应支撑如下结论：

> 跨分片事务的处理阶段与提交阶段之间存在不可避免的异步窗口。在缺乏全局排序、冲突检测或资源锁定机制时，攻击者可以利用该窗口使后到事务在目标分片上抢先提交，从而造成业务语义层面的顺序反转。全局序列号、冲突 key 队列化、OCC 和两阶段提交可以显著降低抢占式提交成功率，但会带来尾延迟上升、回滚率增加或吞吐下降等代价。
