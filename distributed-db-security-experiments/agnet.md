# Codex 实验执行任务书：分布式数据库攻击与防御补充实验

## 背景与目标

当前论文第2章系统讨论了分布式数据库系统中的新型攻击，包括数据分发机制攻击、共识层 Leader DoS、跨分片事务抢跑等；但第4章实证评估主要覆盖 SQL 注入、密码攻击和数据级加密开销。请补充一组可复现的分布式架构攻击与防御实验，用于回应审稿意见中“理论分类与实证评估覆盖度不匹配”的问题。

核心目标不是证明某个真实产品存在漏洞，而是在可控环境中量化三类分布式架构风险及对应防御机制的效果：

1. 数据分发机制风险：确定性路由攻击与混淆路由防御。
2. 共识与副本调度风险：TiDB Leader 压力攻击/网络扰动下的可用性与恢复能力。
3. 跨分片事务顺序风险：异步窗口下的抢占式提交模拟评估。

## 实验一：确定性路由攻击与混淆路由防御评估

### 实验对象

构建两类环境：

- PostgreSQL 3 分片：3 个 PostgreSQL 容器分别作为 shard-0、shard-1、shard-2，前置一个简单路由层，比较 `item_id mod 3` 确定性路由与带 secret salt 的哈希虚拟桶混淆路由。
- TiDB：部署最小可运行 TiDB 集群，建议包含 1 个 TiDB Server、3 个 TiKV、3 个 PD。若服务器资源不足，可先降低规模，但要在报告里说明。

### 攻击场景

设置三组流量：

- 均匀流量：请求均匀分布到 3 个分片。
- 中度目标分片流量：70% 请求来自攻击者按公开路由规则筛选出的目标 key 集合。
- 高度目标分片流量：90% 请求来自攻击者按公开路由规则筛选出的目标 key 集合。

请求类型建议使用读写混合负载，例如：

- 70% `SELECT`
- 20% `UPDATE`
- 10% `INSERT`

### 路由/防御组

实验一聚焦第3章表15中的“混淆路由”思想，至少实现三组对照：

- 确定性路由：`shard_id = item_id % 3`，作为公开路由基线。
- 混淆路由模拟：`shard_id = sha256(secret_salt:item_id)` 经虚拟桶重映射后落到物理分片。
- 混淆路由+流量控制：在混淆路由基础上叠加分片级流量控制，可作为可选扩展，不作为正文重点。

目标流量不要使用单个热点 key，而应使用攻击者按公开确定性规则筛选出的一批 key，例如 `item_id % 3 == 0` 的 key 集合。这样才能评估混淆路由是否降低攻击者精准命中目标分片的能力。

### 指标

记录以下数据：

- 总吞吐量。
- 平均延迟、P95、P99 延迟。
- 请求失败率、超时率。
- 每个分片的 CPU、内存、连接数或活跃事务数。
- 热点物理负载比：公开目标分片0的已路由物理请求量与其他两个分片平均请求量之比。
- 防御开销：正常均匀流量下启用混淆路由或叠加流量控制后的吞吐变化和延迟变化。

### 预期论文结论

该实验应支撑如下结论：

> 确定性路由攻击的请求可以表现为合法数据库访问，因此传统基于 SQL 语法特征的 WAF/IDS 难以直接识别。攻击者若知道公开 `item_id mod 3` 规则，可以筛选一批会落到同一目标分片的 key；混淆路由通过隐藏或改变 key 到分片的映射，降低攻击者精准命中目标分片的能力，但会引入一定映射和运维开销。

## 实验二：TiDB 共识 Leader 压力攻击/网络扰动下的可用性与恢复评估

### 实验对象

使用 TiDB 集群：

- 1 个或 2 个 TiDB Server。
- 3 个 TiKV 节点。
- 3 个 PD 节点。

建议使用 TiUP 或 Docker Compose 部署。若使用 TiUP，需在 README 中写清版本、拓扑和启动命令。

### 攻击/扰动场景

本实验不要写成“复现共识漏洞”，而应写成：

> 共识 Leader 节点压力攻击与网络扰动下的可用性评估。

至少设计三组：

- 正常基线：无扰动，运行标准读写负载。
- Leader 压力：定位热点 Region Leader 所在 TiKV，对该节点施加 CPU 压力、I/O 压力或请求压力。
- 网络扰动：对 Leader 所在 TiKV 注入延迟、抖动或短时丢包，可使用 `tc/netem` 或容器网络限制。

如能实现，加入恢复组：

- 解除压力后观察恢复时间。
- 触发或等待 Leader 转移，观察业务恢复情况。

### 指标

记录以下数据：

- 正常期、攻击/扰动期、恢复期的吞吐量。
- 平均延迟、P95、P99 延迟。
- 请求失败率、超时率。
- Leader 转移是否发生。
- Leader 转移耗时。
- 恢复时间，即指标恢复到基线 90% 或 95% 所需时间。
- TiKV 节点 CPU、内存、磁盘 I/O。

### 防御/缓解分析

重点观察：

- TiDB/PD 调度是否能迁移热点或 Leader。
- 限流是否能降低尾延迟。
- 热点调度与 Leader 转移对可用性的恢复效果。

### 预期论文结论

该实验应支撑如下结论：

> 基于 Leader 的共识和副本调度机制在正常情况下能够提高一致性与系统效率，但当 Leader 所在节点遭受资源压力或网络扰动时，系统可用性会出现明显退化。调度、Leader 转移和限流机制能够缓解故障影响，但恢复过程存在非零时间窗口，说明分布式数据库防御不能只依赖应用层或外围规则，还需要关注共识层和调度层的韧性。

## 实验三：跨分片事务异步窗口下的抢占式提交模拟评估

### 定位

本实验使用 PostgreSQL 3 分片构建可控模拟环境，用于抽象刻画跨分片事务在处理阶段与提交阶段之间存在异步窗口时可能产生的顺序操控风险。

不要写成：

> 复现 TiDB 跨分片抢跑漏洞。

应写成：

> 跨分片事务异步窗口下的抢占式提交模拟。

TiDB 可作为成熟分布式事务机制的对照环境，用来说明全局时间戳、事务冲突检测和提交顺序约束对该类风险的缓解效果。

### 业务场景

建议使用“库存抢购”或“账户转账”场景。优先推荐库存抢购，容易解释：

- shard-0：用户请求或用户账户。
- shard-1：商品库存。
- shard-2：订单确认。

一次跨分片事务流程：

1. 在 shard-0 校验用户资格。
2. 在 shard-1 扣减库存。
3. 在 shard-2 写入订单确认。

### 攻击模拟

构造两个事务：

- `T_victim`：正常用户事务，先到达系统。
- `T_attacker`：攻击者事务，后到达入口，但利用阶段间延迟，在目标分片上先完成库存扣减或订单确认。

模拟方式：

- 在 `T_victim` 完成 shard-0 校验后，人为加入网络/处理延迟。
- `T_attacker` 在延迟窗口内发起冲突请求。
- 如果 `T_attacker` 先在 shard-1 完成库存扣减，则记为一次抢占式提交成功。

### 防御组

至少实现以下对照：

- 无防御：各分片按本地到达顺序处理。
- 全局序列号：入口路由层为事务分配全局递增序号，目标分片按序提交。
- 版本检查/OCC：提交前检查库存版本号或账户版本号，冲突则回滚后到事务。
- 冲突键队列化：同一商品、账户或资产键的跨分片事务串行执行。
- 两阶段提交模拟：prepare 阶段锁定目标资源，commit 阶段统一确认。

### 指标

记录以下数据：

- 抢占式提交成功率：后到事务先提交的比例。
- 一致性违规率：库存超卖、余额异常、订单顺序反转等。
- 事务回滚率。
- 平均延迟、P95、P99 延迟。
- 吞吐量。
- 防御开销：全局排序、冲突队列、OCC 或两阶段提交引入的吞吐下降与延迟增加。

### 预期论文结论

该实验应支撑如下结论：

> 跨分片事务的处理阶段与提交阶段之间存在不可避免的异步窗口。在缺乏全局排序、冲突检测或资源锁定机制时，攻击者可以利用该窗口使后到事务在目标分片上抢先提交，从而造成业务语义层面的顺序反转。全局序列号、冲突键队列化、OCC 和两阶段提交可以显著降低抢占式提交成功率，但会带来尾延迟上升、回滚率增加或吞吐下降等代价。
